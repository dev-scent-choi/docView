# 엑셀 동시편집기 진짜 윈도우 방식 지연 로딩 (Design)

## 배경 및 목표

대형 xlsx를 동시편집기(editor-grid.html)로 열면, 지금은 파일 전체를 파싱해 모든 셀을 Yjs
공유문서(CRDT)에 한 번에 시딩하고, 클라이언트도 전체 행만큼 테이블 DOM을 한 번에 그린다.
이 세션에서 이미 "파싱·시딩 루프가 이벤트 루프를 막아 서버 전체가 멈추는" 급한 버그는 별도로
고쳤다(커밋 `6355a17`). 이 스펙은 그 다음 단계 — **화면에 필요한 부분만 로드·렌더링하는 진짜
지연 로딩**을 다룬다.

목표: 수십만 행짜리 시트를 열어도 (1) 서버 메모리에 Yjs CRDT로 유지되는 데이터량이 "지금 누군가
보고 있는 부분"으로 제한되고, (2) 클라이언트가 만드는 테이블 DOM도 화면에 보이는 행만큼으로
제한되어, 파일 크기와 무관하게 빠르게 열리고 가볍게 유지된다.

## 핵심 설계 결정 (브레인스토밍에서 확정)

- **화면 밖 셀을 참조하는 수식 문제는 수식 계산을 서버로 옮겨서 해결한다.** 서버는 항상 전체
  데이터를 갖고 있으므로 어떤 참조든 정확히 계산할 수 있다. 클라이언트는 계산된 표시값만 받는다.
- **Yjs는 "지금 보이는 페이지"만 담는 캐시다.** 진짜 데이터(canonical)는 서버가 항상 전체를
  메모리에 들고 있다. 뷰어가 이미 쓰는 500행 페이지 단위를 그대로 재사용한다.
- **페이지 안에서의 편집은 지금처럼 Yjs CRDT로 실시간 동시편집된다.** 다만 그 편집은 발생 즉시
  (자동저장 주기를 기다리지 않고) canonical 데이터에도 반영된다 — 그래야 편집 직후 다운로드/저장
  요청이 항상 최신 상태를 본다.
- **저장·다운로드는 항상 canonical 데이터에서 내보낸다.** Yjs 상태와 무관하게 항상 최신이고
  완전하다.
- **클라이언트 테이블 DOM도 보이는 행만 가상 렌더링한다.** 안 그러면 서버·Yjs 쪽을 다 고쳐도
  브라우저가 수십만 개 `<tr>`을 만들다 멈춘다.

## 아키텍처 개요

```
[클라이언트]                          [서버: room.ts]
  가상 스크롤 테이블                     canonical GridDocument (전체, 항상 메모리)
  (보이는 행 + 여유분만 DOM)                │
      │ 보이는 페이지 계산                  │ 페이지 구독 관리(클라이언트별)
      │ (디바운스 200ms)                    │
      ▼                                    ▼
  구독 메시지(sheet, pages[]) ──WS──▶  구독 페이지 합집합 계산
                                            │
                                            ▼
                                     그 페이지 셀만 Yjs
                                     cells/styles/computed 맵에 채움
      ◀──Yjs sync(y-websocket)────────────┘
  화면에 표시(cells 또는 computed 값)

  셀 편집(Yjs cells.set) ──Yjs update──▶  즉시 canonical에도 반영
                                            + 그 페이지의 수식 셀 재계산
                                            + 결과를 computed 맵에 반영

[저장/다운로드]  flushToStore / getCurrentBytes ──▶ 항상 canonical에서 직렬화
```

## 데이터 모델

### 서버: canonical 그리드

기존 `parseXlsxToGrid`가 만드는 `GridDocument`(`src/spreadsheet.ts`)를 그대로 재사용하되,
룸이 열려 있는 동안 서버 메모리에 계속 유지한다(지금처럼 Yjs에 통째로 시딩한 뒤 버리는 게
아니라, `Room` 인터페이스에 `canonicalGrid: GridDocument`와 각 셀의 편집 여부를 구분할
베이스라인을 추가로 들고 있는다).

셀 하나당 "원본값(baseline)"과 "현재값"을 구분해야 저장 시 손대지 않은 수식·서식이 안
깨진다 — 지금 Yjs의 `cells`+`baseline`, `styles`+`stylesBaseline` 네 쌍과 같은 개념을
서버 쪽 구조로 옮긴다(정확한 자료구조는 계획 단계에서 확정).

### Yjs: 페이지 캐시 (companion 맵 추가)

기존 `GRID_CELLS_MAP`/`GRID_STYLES_MAP`(`src/collab/gridShared.ts`)은 그대로 두되, 이제
"현재 구독 중인 페이지의 셀만" 채워진다는 의미로 바뀐다. 새로 추가:

- `GRID_COMPUTED_MAP`(`'computed'`) — 수식 셀의 계산된 표시값만 담는 Y.Map, `cells`와 같은
  `"시트:행:열"` 키. 수식이 아닌 셀은 이 맵에 항목이 없다. 클라이언트는 표시할 때
  `computed.get(key) ?? cells.get(key)`로 읽는다(`cells`는 항상 원본 텍스트 — 수식이면
  `"=SUM(...)"` 그 자체 — 를 담아, 셀을 클릭했을 때 수식 입력창에 그대로 보여줄 수 있게 한다).

**중요: `GRID_STRUCTURE_MAP`/`GRID_MERGES_MAP`(시트 이름, 전체 행/열 수, 틀고정, 병합 정보)은
윈도잉 대상이 아니다 — 모든 시트에 대해 항상 전체가 Yjs에 있다.** 클라이언트가 스크롤 가능한
전체 높이를 계산하고(가상 스크롤에 필수), 시트 탭을 그리고, 아직 로드 안 된 페이지의 병합 셀
경계를 미리 알려면 이 메타데이터가 페이지 구독과 무관하게 항상 필요하다. 윈도잉되는 건 오직
**셀 값·서식**(`cells`/`styles`/`computed`)뿐이다.

### 서버 ↔ 클라이언트: 페이지 구독 프로토콜

`room.ts`의 기존 바이너리 메시지 프로토콜(`MESSAGE_SYNC = 0`, `MESSAGE_AWARENESS = 1`)에
새 메시지 타입을 추가한다: `MESSAGE_PAGE_SUBSCRIBE = 2`, payload는
`{ sheet: number; pages: readonly number[] }`(JSON, UTF-8 인코딩) — "이 클라이언트가 지금
이 시트의 이 페이지 번호들(0-based, 500행 단위)을 보고 있다"를 통째로 알린다(추가/삭제
diff가 아니라 매번 "지금 전체 목록"을 보낸다 — 프로토콜을 단순하게 유지하기 위한 선택,
디바운스로 전송 빈도 자체를 줄인다).

**시트 전환**: 이 메시지는 항상 "그 클라이언트가 지금 보고 있는 유일한 (시트, 페이지 목록)"을
통째로 대체한다 — 클라이언트가 시트 탭을 바꾸면 새 시트의 페이지 목록으로 다시 보내고,
서버는 그 클라이언트의 이전 구독(옛 시트의 페이지들)을 이 메시지로 완전히 덮어쓴다. 클라이언트가
동시에 두 시트를 구독하는 경우는 없다(그리드 편집기는 한 번에 시트 하나만 활성화되어 있다는
기존 UI 전제와 일치).

## 클라이언트: 가상 스크롤 + 구독

- 테이블은 전체 행 수만큼의 높이를 가진 스크롤 컨테이너 안에, "보이는 행 범위 + 여유분(±1
  페이지 정도)"만 실제 `<tr>`로 그린다. 행 높이는 고정값으로 근사(뷰어의 페이지 크기 캐시처럼
  실측하지 않는다 — 일부 행이 줄바꿈으로 더 높아져도 스크롤 위치가 살짝 어긋나는 정도는
  허용하는 실무적 타협).
- 스크롤이 멈추고 200ms 뒤에 보이는 범위가 속한 페이지 번호들을 계산해 구독 메시지를 보낸다
  (스크롤 중 매 프레임 전송 방지).
- 서버는 클라이언트별 구독 페이지를 추적하고(연결이 끊기면 즉시 제거), 룸에 접속한 모든
  클라이언트의 구독 페이지 합집합만 Yjs에 채운다. **합집합에 새로 들어온 페이지는 즉시
  채우지만, 합집합에서 빠진 페이지는 바로 지우지 않고 일정 시간(예: 10초) 아무도 다시
  구독하지 않을 때만 지운다** — 사용자가 페이지 경계 근처에서 위아래로 스크롤을 반복하면
  같은 페이지가 추가·제거를 계속 반복해 매번 Yjs 항목을 다시 만들고 지우는 낭비(및 그때마다
  발생하는 update 이벤트 폭주)가 생기기 때문이다. 지연 제거 중에도 canonical에는 항상 최신이
  반영되어 있으므로 데이터 유실 위험은 없다.

## 수식 계산

`fast-formula-parser`(현재 클라이언트가 쓰는 라이브러리, `src/client/grid-editor.ts`)와
`src/client/formulaOverrides.ts`의 커스텀 함수 구현을 서버(`src/collab/room.ts` 또는 새
`src/xlsx/formulas.ts`)로 옮긴다. `onCell`/`onRange` 콜백이 이제 canonical 그리드를 직접
읽으므로 화면 밖 참조도 항상 정확하다.

계산 시점: 의존성 그래프 없이(지금 클라이언트 방식과 동일한 단순함 유지, 범위 절제) —
(1) 어떤 셀이든 편집되면 "지금 구독 중인 모든 페이지"의 수식 셀을 다시 계산해 `computed` 맵에
반영하고, (2) 새 페이지가 구독되면 그 페이지의 수식 셀도 그때 계산한다.

클라이언트는 더 이상 수식을 직접 계산하지 않으므로 `fast-formula-parser`를
`grid-editor.ts`(클라이언트 번들)에서 제거하고 서버 쪽 의존성으로만 남긴다.

## 저장·다운로드

`src/collab/room.ts`의 `flushToStore`(자동저장) xlsx 분기와 `getCurrentBytes`(즉시 다운로드)
는 더 이상 Yjs에서 셀을 읽지 않고, 룸이 들고 있는 canonical 그리드에서 직접
`exportXlsxFromGrid`에 준하는 직렬화를 수행한다(정확한 함수 시그니처 변경은 계획 단계에서
확정). 페이지 편집이 즉시 canonical에 반영되므로(위 아키텍처 참고) 별도 동기화 대기 없이
항상 최신 상태를 내보낸다.

## 에러·엣지 케이스

- **스크롤 중 구독 폭주**: 200ms 디바운스로 방지(위 클라이언트 섹션).
- **페이지 구독 해제 시 데이터 유실**: 편집이 즉시 canonical에 반영되므로 유실 없음. 재구독 시
  canonical 기준으로 다시 채운다(최초 로드와 동일한 경로 재사용).
- **재연결**: 클라이언트가 재연결하면 구독 페이지 목록을 다시 보낸다. 서버는 연결 종료 시 그
  클라이언트의 구독을 즉시 제거한다(`closeConn`, 기존 로직 확장).
- **화면 밖 큰 범위를 참조하는 수식**(예: `SUM(A1:A300000)`): canonical이 전체를 갖고 있어
  계산은 되지만 느릴 수 있다 — 지금 클라이언트에서도 겪던 성능 특성이라 이번 설계로 새로
  생기는 리스크가 아니므로 범위 밖으로 둔다.
- **수식 재계산이 서버 이벤트 루프를 막을 위험**: 이번 세션 앞부분에서 xlsx 파싱/시딩이
  양보 지점 없는 동기 루프라 서버 전체가 멈추는 버그를 고쳤다(`6355a17`) — 수식 재계산도
  같은 함정에 빠질 수 있다(넓은 범위를 참조하는 수식이 많은 페이지를 재계산하면 동기 루프가
  길어진다). **수식 재계산 루프도 같은 양보 지점 패턴(`yieldToEventLoop`,
  `src/spreadsheet.ts`)을 반드시 재사용한다** — 이건 선택이 아니라 이 스펙이 준수해야 할
  제약으로 취급한다(아래 전역 제약 참고).
- **페이지 반복 추가/삭제로 인한 Yjs 내부 이력 누적**: 사용자가 페이지 경계 근처에서 스크롤을
  반복하면(위 지연 제거로 크게 줄지만 완전히 없앨 수는 없다) Y.Map 항목의 추가·삭제(tombstone)
  이력이 쌓인다. `room.ts`는 이미 룸의 `Y.Doc`을 `{ gc: true }`로 생성하므로(기존 코드) Yjs가
  이 이력을 주기적으로 정리한다 — 별도 조치는 필요 없지만, 실측에서 문제가 보이면 지연 제거
  유예 시간(10초)을 늘리는 방향으로 대응한다(코드 변경 없이 상수 조정만으로 완화 가능하도록
  설계).
- **서버 재시작 시 룸 재생성**: canonical을 채우려면 여전히 파일 전체 파싱이 필요하지만(항상
  전체가 있어야 하므로), 이 세션 앞부분에서 이미 고친 양보 지점(`6355a17`) 덕에 그 파싱 자체가
  서버를 멈추게 하지는 않는다. 예전처럼 Yjs 전체 시딩(가장 무거웠던 CRDT 오버헤드)은 이제
  구독된 페이지만큼만 하므로 룸을 여는 비용 자체가 훨씬 가벼워진다.

## 핵심 제약 (구현 시 반드시 지켜야 함)

- **canonical 그리드를 훑거나 채우는 모든 반복문(파싱, 수식 재계산, 페이지 채움/비움)은
  `src/spreadsheet.ts`의 `yieldToEventLoop`/`YIELD_EVERY_N_ROWS` 패턴을 재사용해 이벤트
  루프를 막지 않는다.** 이 세션에서 겪은 "대형 xlsx가 서버 전체를 멈추는" 버그(`6355a17`로
  수정)가 이번 설계의 새 반복문(특히 수식 재계산)에서 재발하지 않도록 하는 가장 중요한 제약.
- **Yjs `cells`에는 항상 원본 텍스트(수식이면 수식 자체)만 담는다.** 계산된 표시값은 반드시
  `GRID_COMPUTED_MAP`에만 쓴다 — 섞으면 저장 시 수식이 정적 값으로 깨지는, 이 프로젝트가 이미
  한 번 겪은 버그 클래스가 재발한다(`src/xlsx/collab.ts`의 `seedableCellValue` 관련 주석 참고).
- **셀 편집이 발생하면 그 트랜잭션 안에서(또는 같은 이벤트 처리 안에서) canonical 반영까지
  끝낸다** — "나중에 배치로 반영" 같은 지연을 두면 편집 직후 다운로드가 최신을 못 보는,
  브레인스토밍에서 사용자가 직접 지적해 확정한 요구사항을 위반한다.
- **`GRID_STRUCTURE_MAP`/`GRID_MERGES_MAP`은 절대 윈도잉하지 않는다** — 항상 모든 시트의
  전체 메타데이터가 Yjs에 있어야 클라이언트가 로드 안 된 페이지의 스크롤 높이·병합 경계를
  미리 알 수 있다.

## 범위 밖 (이번 설계에서 다루지 않음)

- 수식 의존성 그래프 기반 증분 재계산(지금도 없는 최적화, 이번에도 안 만든다).
- docx/pptx 편집기의 지연 로딩(엑셀과 구조가 달라 각자 별도 스펙 대상 — 이전에 합의한 4단계
  계획의 남은 항목).
- 행 높이 실측 기반 정밀 가상 스크롤(고정 높이 근사로 충분하다고 판단).
- 페이지 구독 diff 프로토콜(추가/삭제만 전송) — 매번 전체 목록을 보내는 단순한 방식으로 시작.

## 테스트 방침

- 서버: canonical 그리드 유지, 페이지 구독에 따른 Yjs 채움/비움, 편집 즉시 canonical 반영,
  수식 재계산(화면 밖 참조 포함), 저장/다운로드가 canonical에서 정확히 내보내는지 — 각각
  단위/통합 테스트로 검증(정확한 테스트 케이스는 계획 단계에서 브리프에 코드로 명시).
- 클라이언트: 가상 스크롤이 만드는 DOM 행 수가 전체 행 수와 무관하게 일정 범위로 유지되는지,
  스크롤에 따라 구독 메시지가 올바른 페이지 번호로 나가는지 — 이 프로젝트의 기존 관례상
  자동화된 DOM 테스트 하네스가 없으므로(뷰어도 마찬가지), 실제 대형 파일로 브라우저 확인을
  병행한다.
