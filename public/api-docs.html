그 외 엔드포인트

DocView는 4~5개의 REST API만으로 연동한다 — 업로드하고, 상태(및 실시간 변경 이력)를 폴링하고, 열람/편집 토큰을 발급해 <iframe>으로 띄우고, 필요하면 최신 파일을 내려받는다. 이 페이지는 README.md의 "다른 프로젝트에서 연동하기" 절을 그대로 옮긴 것이라, 최신 내용은 두 문서가 항상 같다.

1문서 업로드
→
2GET으로 status:'ready' 폴링
→
3토큰 발급
→
4editorUrl/viewerUrl을 iframe으로 임베드
→
5(선택) 다운로드

응답 형식

모든 API는 같은 봉투(envelope)를 쓴다 — 성공/실패를 success 불리언으로 구분하고, 실패 시 사람이 읽을 수 있는 한국어 error 메시지를 준다(에러 메시지 문자열 자체를 파싱해 분기하지 말고, HTTP 상태 코드로 분기할 것을 권장한다).

성공
{ "success": true, "data": { /* 엔드포인트마다 다름 */ } }
실패
{ "success": false, "error": "문서를 찾을 수 없습니다." }

429(속도 제한 초과)만 예외로 statusCode 필드가 하나 더 붙는다 — 인증 절 참고.

인증

업로드·토큰 발급·삭제처럼 아무나 호출하면 안 되는 API는 Authorization: Bearer <발급받은 키> 헤더를 요구한다. 키는 서버 환경변수 DOCVIEW_API_KEYS에 "이름:키,이름2:키2" 형식으로 프로젝트별로 등록한다 — 반드시 서버 사이드에서만 호출해야 한다(키가 브라우저 자바스크립트에 노출되면 안 된다).

DOCVIEW_API_KEYS가 아예 설정돼 있지 않으면(로컬 개발 등) 이 검사 자체를 건너뛴다. 운영 배포에서는 반드시 설정한다.

키가 없거나 틀리면 다음을 401로 돌려준다:

{ "success": false, "error": "API 키가 없거나 유효하지 않습니다." }

다운로드 API는 API 키가 아니라, 토큰 발급 API로 받은 열람 토큰(URL의 ?token=)으로 인증한다 — 이 토큰은 만료 시간이 있는 서명된 JWT라 API 키보다 훨씬 좁은 권한(문서 하나, 정해진 권한만)을 가진다.

속도 제한

업로드·토큰 발급·삭제(쓰기 성격의 API 키 엔드포인트)는 IP당 속도 제한이 있다 — 업로드· 삭제는 분당 30회, 토큰 발급은 다른 시스템이 사용자가 문서를 열 때마다 호출할 수 있어 더 넉넉하게 분당 120회다. 초과하면 429와 함께 Retry-After 헤더(초 단위)를 돌려준다:

{ "statusCode": 429, "success": false, "error": "요청이 너무 많습니다. 42 seconds 후 다시 시도하세요." }

조회·다운로드 계열(상태 조회, 다운로드) 에는 속도 제한이 없다 — 뷰어 화면이 페이지를 넘기거나 그리드를 스크롤할 때마다 정상적으로 자주 호출하기 때문이다.

문서 업로드

API 키 필요

같은 처리 로직을 타므로 둘 중 편한 방식을 쓰면 된다 — 결과(응답 모양)는 동일하다.

POST /api/documents

multipart/form-data, 파일 필드명은 file. 파일 필드가 있는 폼 전송에 이미 익숙한 쪽에 맞다.

POST /api/documents/stream?filename=문서.pptx

요청 본문에 파일 바이트를 그대로 싣는다(Content-Type: application/octet-stream). multipart 경계를 직접 구성할 필요가 없어, 같은 서버(또는 같은 파일시스템)에 원본이 이미 있는 호출자가 디스크에서 바로 읽어 스트림으로 파이프하기에 특히 편하다.

쿼리 파라미터 (stream 방식만)

이름타입설명
filename필수string (1–300자)원본 파일명(확장자 포함) — 저장될 형식 판별에 쓰인다.
예시 (stream 방식, curl)
curl -X POST \
  --data-binary "@/path/to/문서.pptx" \
  -H "Content-Type: application/octet-stream" \
  -H "Authorization: Bearer <발급받은 키>" \
  "https://<이 서비스 주소>/api/documents/stream?filename=문서.pptx"

Node에서는 파일을 버퍼로 먼저 다 읽지 않고 fetch(url, { method: 'POST', body: fs.createReadStream(path), duplex: 'half', headers: {...} })처럼 스트림을 body에 그대로 넘기면 된다.

{
  "success": true,
  "data": {
    "id": "3c5cf246-3de2-4107-8028-073bab533f61",
    "name": "문서.pptx",
    "ext": "pptx",
    "status": "processing",
    "pageCount": 0,
    "createdAt": "2026-09-21T04:19:04.786Z",

}

status는 업로드 직후 대개 "processing"이다 — 상태 조회 API로 "ready"가 될 때까지 폴링한다.

인증 불필요

변환 상태를 status: "ready"가 될 때까지 폴링한다. xlsx/docx/pptx이고 지금 동시편집 룸이 열려 있으면(누군가 편집기를 켜 놓은 상태) 응답에 changes 배열이 함께 실린다 — 룸이 열린 시점 대비 누적된 변경 내역이다.

응답 200

{
  "success": true,
  "data": {
    "id": "…", "name": "문서.docx", "ext": "docx",
    "status": "ready", "pageCount": 4,
    "createdAt": "…", "progress": 100,
    "changes": [ /* 아래 참고, 룸이 없으면 항상 [] */ ]
  }
}

changes — 문서 형식(ext)마다 항목 모양이 다르다

xlsx — 셀 단위 (row/col은 엑셀 A1 표기에 맞춘 1-based):

{ "sheet": 0, "row": 2, "col": 1, "before": "Alice", "after": "Bob", "viewer": "김철수", "at": "2026-09-18T12:42:59.249Z" }

docx — 문단 단위:

{ "paragraph": 4, "before": "구분", "after": "구분[수정]", "viewer": "이영희", "at": "2026-09-19T00:10:36.637Z" }

paragraph는 현재 문서 순서 기준 1-based 문단 번호(표 셀·목록 항목 안의 문단도 똑같이 센다). 삭제된 문단은 paragraph: null·after: "", 새로 추가된 문단은 before: ""다. 글자 서식만 바뀐 편집은 보고하지 않는다. 문단이 삽입/삭제되면 번호가 밀리므로 paragraph는 안정적인 식별자가 아니다 — before+at 조합으로 이력을 쌓는 것을 권장한다.

pptx — 슬라이드/텍스트박스 단위, kind가 세 가지다:

{ "kind": "text", "slideId": "9f1c…", "slide": 3, "originalSlide": null, "shape": "2", "before": "제목", "after": "제목(수정)", "viewer": "박민수", "at": "…" }
{ "kind": "slide_added", "slideId": "c07a…", "slide": 5, "originalSlide": null, "shape": null, "before": "", "after": "", "viewer": "박민수", "at": "…" }
{ "kind": "slide_removed", "slideId": "51de…", "slide": null, "originalSlide": 2, "shape": null, "before": "", "after": "", "viewer": "박민수", "at": "…" }

slide는 조회 시점의 현재 덱 순서 기준 1-based 번호라 슬라이드가 삭제·추가되면 밀린다 — 삭제된 슬라이드는 대신 originalSlide(룸이 열릴 때의 위치)를 준다. slideId는 룸이 열려 있는 동안 순서가 바뀌거나 다른 슬라이드가 지워져도 그대로인 식별자라, 안정적인 upsert 키로 쓰기 좋다.

DB가 아니라 메모리에만 있는 값이다. 룸이 닫히면(모든 편집자가 나가서 파일로 flush되면) changes는 그 즉시 []가 된다 — "지금 아무도 안 보고 있다"와 "변경이 없었다"를 구분하지 않는다. 저장 시점마다 초기화하지 않고 계속 누적되므로, 같은 문서를 여러 번 polling하면 이미 받은 항목을 다시 받을 수 있다(호출하는 쪽에서 upsert 필요 — xlsx는 sheet,row,col, docx는 before+at, pptx는 slideId+shape+kind). hwp는 아직 지원하지 않는다(항상 []).

룸이 닫힐 때 디스크에도 남는다(안전망)

편집 중이던 연동 측이 그 사이 한 번도 polling하지 못했거나 호출이 일시적으로 실패했다면, 룸이 닫히는 순간(마지막 편집자 퇴장) 그때까지 쌓인 항목 전체가 서버의 data/changeLogs/changes-YYYY-MM-DD.jsonl(UTC 날짜 기준)에 한 줄씩 append된다. 각 줄은 위 changes 항목에 docId, docKind("xlsx"/"docx"/"pptx"), closedAt을 얹은 모양이다. 이건 fire-and-forget 안전망이지 조회 API가 아니다 — 이 파일을 읽어 돌려주는 엔드포인트는 없고, 서버가 스스로 지우지도 않는다(로그 보관 정책은 배포 환경의 일반적인 방식(logrotate 등)에 맡긴다). 룸이 "정상적으로" 닫힐 때만 기록하므로, 서버가 죽거나 재시작되면 그 세션의 변경 이력은 디스크에도 남지 않는다(문서 내용 자체는 별도 자동저장으로 안전하다).

엔드포인트설명

GET /api/formats업로드 가능한 확장자 목록.

maintenance-management의 "업체별 접속현황" 탭이 이 API들로 실제 연동되어 있다 — 소비자 관점의 자세한 흐름은 그 프로젝트의 WEBVIEWER_INTEGRATION.md 참고. 이 페이지 자체는 저장소 루트 README.md의 "다른 프로젝트에서 연동하기" 절과 내용이 같다 — 둘 중 하나만 고치고 나머지를 잊지 않도록, API가 바뀌면 항상 같이 갱신한다.
